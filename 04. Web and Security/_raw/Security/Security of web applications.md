# Security of web applications

Что можно атаковать?

- Клиент (client-side vulnerabilities)
- Сервер (server-side vulnerabilities)

## Серверные уязвимости

**Логические** (ошибки в разраничении прав доступа, изыбточная/небезопасная функциональность, наружение логики работы приложения). Эти узявимости специфичны для проекта. Обычно должы быть найдены при тестировании.

Пример:
**IDOR** (Insecure Direct Object Reference)
Доступ к ресурсам которые не должны быть доступны пользователю
```curl
GET /messages/123 HTTP/1.1
GET /messages/124 HTTP/1.1
```

Ошибки реализации

- Инъекции и небезопасная десериализация
- Гонки (race conditions)
- Раскрытие информации, открытые редиректы и тд

**Insecure Deserialization**
Языки программирования имеют встроенные средства сериализации/десериализации програмных сущностей. Это значит что если на такой десериализатор передать объект с вредоносным кодом, то он может быть выполнен после десериализации

Решение:
- использовать "безопасные" форматы (JSON, Protobuf)
- Если нельзя использовать безопасный формат, то нужно использовать контроль целостности (хеш функция)

**XML External Entities** / XXE
XML очень сложный формат с множеством различных функций. Есть возможности для выполнения кода на сервере. Есть возможности подключать стороние файлы на сервере.
Есть возможность положить сервер циклом
Есть возможность делать запросы на другой сервер 
Разные библиотеки и языки программирования используют разные библиотеки для XML

Решение:
- Отключить лишнее (парсинг DTD, XXE и тд)
- Не использовать XML

**CRLF Injection & HTTP Parameter contamination**
Протоколы HTTP 1.0 и 1.1 текстовые (не бинарные).
В запрос могут быть добавлены управляющие последовательности, которые могут видоизменить запрос

**Path traversals**
Если сервер отдает файл с файловой системы сервера, то атакующий может получить файл по другому пути

- Не используйте файловую систему

**Гонки (race conditions)**
Если сделать запрос 2 раза очень быстро то если код плохой и нет транзакций, то можно сделать уязвимость


**Раскрытие информации**
Если сохранить куки логов то можно авторизоваться под пользователем если получить доступ к логам

Раскрытие в заголовках или еще где-то что использутеся на сервере (веб сервер и версия, язык программирования и тд)

Secret managment - также классическая ошибка хранение секретов в общем репозитории или еще как-то ненадежно

JWT - пейлоад не зашифрован, нельзя класть в пейлоад информацию которая может раскрыть данные пользователя

**Открытые редиректы**
Если на сайте есть ссылки редиректы с открытым назначением для редиракта, например:
http://google.com/redirect=http://attacker.com
то атакующий может дать ссылку атакуемому и тот может не заметить в ссылке редирект, особено если ссылка для редиректа url encoded



Открытые редиректы позволяют развивать атаки XSS и SSRF

## CORS и Same Origin Policy (SOP)

CORS блокирует получение в браузере ответа от сервера с другого ресурса (хост порт).

Пример:
У пользователя есть активная сессия с кукой в банковском приложении.
Есть зловредный сайт.
Зловредный сайт направлен на тех, кто пользутеся этим банковским приложением.

Когда пользователь попадает на зловредный сайт, на нем выполняется джаваскрипт, который отправляет аякс запрос фоном на апи банка на перевод стредств (надуманый пример, но демонстрирует смысл).

Такой запрос называется **межсайтовым**. Браузер считает межсайтовыми запросы в которых хост и порт страницы откуда сделали запрос не равен хосту и порту ресурса куда сделан запрос. 

Далее браузер отправляет запрос OPTIONS на ресурс, если считает **этот запрос простым**.
В ответе сервера браузер будет ожидать увидеть заголовки:
- `Access-Control-Allow-Origin` 
- `Access-Control-Allow-Methods`
- `Access-Control-Allow-Headers`

Если информация из этих заголовков будет совпадать с запросом и хостом, то будет выполнен оригинальный запрос, но так же с проверкой этих хедеров.

Если заголовки не совпадают с запросом то в обоих случаях браузер не позволит обработать **ответ сервера** на запрос.

Однако, если браузер считает оригинальный запрос **сложным**, то запрос `OPTIONS` не будет отправлен. Будет отправлен сразу оригинальный запрос. Т.е. **ЗАПРОС ВСЕ РАВНО БУДЕТ ВЫПОЛНЕН НА СЕРВЕРЕ**, хоть страница зловредного сайта и не сможет получить доступ до результата выполнения.

Признаки, свидетельствующие о сложности запроса:
-   Запрос использует методы отличные от `GET`, `POST`, или `HEAD`
-   Запрос включает заголовки отличные от `Accept`, `Accept-Language` или `Content-Language`
-   Запрос имеет значение заголовка `Content-Type` отличное от `application/x-www-form-urlencoded`, `multipart/form-data`, или `text/plain`.

В случае же, если сервер отдает в заголовках ответа `Access-Control-Allow-Credentials: true` то возникает ситуация, когда становится возможной `CSRF` атака. Сайт злоумышленника может отправлять межсайтовые запросы вместе с куками авторизации. 

Комбинация ниже является антипаттерном (и блокируется браузерами по умалчанию):
```
Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: *
```

## CSRF

Если есть сайт/апи где пользователь авторизован и авторизуется туда по куке, то зловредный сайт может выполнить в джаваскрипте запрос на этот апи от имени этого пользователя (браузер отправит куки, в случае `Access-Control-Allow-Credentials: true`) через аякс. Это может быть очень опасно.

Для апи - если не используются куки, то атака невозможна. Фронтенд может сохранять ключ в локал сторедж и затем отправлять его в хедере при запросе. 

Synchronizer Token Pattern
Laravel, Yii, Symfony use csrf token hidden field in form

Общее решение:
- Правильные настройки CORS политики, неиспользование антипаттернов
- НИКОГДА не использовать CORS header reflection - когда в `Access-Control-Allow-Origin` на сервере автоматически подставляется `HTTP_ORIGIN`
- По возможности не использовать куки

## XSS (Cross-Site Scripting)
Если злоумышленник смог найти уязвимость-инъекцию, то он может внедрить на страницу сайта вредоносный javascript код. Такой код может своровать авторизационные данные, менять страницу и выполнять запросы на сервер от имени клиента

## SSRF (Server-Side Request Forgery)

SSRF атака позволяет сделать запрос от имени атакуемого сервера на другой ресурс.
Атака становится возможной, когда сервер обращается к каким-то сторонним ресурсам и пользователь имеет какой-то контроль на тем на какой ресурс будет запрос или на какие-то из его параметров.
