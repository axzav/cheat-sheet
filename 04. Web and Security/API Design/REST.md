# REST (Representational State Transfer)

Это архитектурный стиль для создания сетевых приложений, который определяет набор ограничений и принципов для проектирования и взаимодействия с веб-службами.
Это не протокол (как SOAP) и не стандарт, а набор рекомендаций, которые делают общение между программами предсказуемым и удобным.
Это способ взаимодействия клиента и сервера, где каждая порция данных (ресурс) имеет свой адрес, и мы манипулируем ими с помощью стандартных методов.

**RESTful API** — это интерфейс, который построен в полном соответствии с принципами REST. Сервер ожидает стандартные HTTP-запросы и отдает данные.

Хотя REST подразумевает использование разных форматов данных (представлений), например, JSON, XML, HTML, **стандартом де-факто является JSON**.

## Основные принципы

### Клиент-серверная архитектура (Client-Server):
Клиент и сервер разделены. Клиенты запрашивают ресурсы, а серверы предоставляют их. Это разделение позволяет независимое развитие клиента и сервера.

### Отсутствие состояния (Stateless):
Каждое взаимодействие между клиентом и сервером не зависит от предыдущих взаимодействий. Вся необходимая информация для выполнения запроса должна быть включена в сам запрос.

### Кеширование (Cacheable):
Ответы могут быть кешируемыми. Это улучшает производительность, снижая необходимость повторных обращений к серверу для получения одних и тех же данных.

### Единообразный интерфейс (Uniform Interface):
Все ресурсы выглядят одинаково, обращение к ним стандартизировано.

- **Идентификация ресурсов**: Каждый ресурс имеет уникальный идентификатор (обычно URL).
- **Манипуляция ресурсами через представления**: Клиенты взаимодействуют с ресурсами, используя их представления (например, JSON, XML).
- **Самоописываемые сообщения**: Сообщения содержат всю необходимую информацию для обработки запроса или ответа.
- **Гипермедиа как движок приложения (HATEOAS)**: Клиенты получают информацию о доступных действиях через гиперссылки в ответах сервера.

### Многоуровневость (Layered System):
Клиент не должен знать, общается он напрямую с сервером или через посредника (балансировщик, прокси).

### Код по запросу (Code on Demand, необязательный):
Сервер может передавать исполняемый код клиенту для выполнения. Например, JavaScript для выполнения на стороне клиента.


## Методы HTTP (Глаголы)

**GET**: Чтение, получить данные о ресурсе (или список);
**POST**: Создание, создать новый ресурс;
**PUT**: Замена, полностью обновить существующий ресурс;
**PATCH**: Частичное обновление, изменить только одно или два поля в ресурсе;
**DELETE**: Удалить ресурс.


## Статусы ответов

### Группа 2xx (Success)
* **200 OK:** Всё прошло успешно.
* **201 Created:** Ресурс создан. Хорошая практика добавь заголовок `Location` со ссылкой на новый ресурс.
* **204 No Content:** Всё успешно, но данных в теле нет (часто для `DELETE` или `PUT` без возврата объекта).

### Группа 4xx (Client Errors)
* **400 Bad Request:** Общая ошибка (например, неверный синтаксис JSON).
* **401 Unauthorized:** Клиент не представился (нет токена).
* **403 Forbidden:** Клиент известен, но у него нет прав на это действие.
* **404 Not Found:** Ресурс не существует.
* **406 Not Acceptable** Сервер не может вернуть ответ запрошенный в заголовке `Accept`.
* **409 Conflict:** Ресурс в таком состоянии, что действие невозможно (например, попытка создать пользователя с существующим email).
* **422 Unprocessable Entity:** (Из WebDAV, но стандарт де-факто для REST). Означает, что JSON синтаксически верен, но нарушена бизнес-логика или правила валидации. **Это лучший код для ошибок в формах.**
* **429 Too Many Requests:** Сработал Rate Limiter.

### Группа 5xx (Server Errors)
* **500 Internal Server Error:** Ошибка сервера, не нужно делать ретрай.
* **503 Service Unavailable:** Сервер временно не может обработать запрос (техобслуживание или перегрузка). Вместе с заголовком `Retry-After` можно сделать ретрай.


## Заголовки

* **`Content-Type`:** Говорит получателю, как парсить тело запроса/ответа. Для REST обычно `application/json`, для RFC 7807 — `application/problem+json`
* **`Accept`:** Клиент говорит серверу в каком формате ждет ответ. Если сервер не может отдать ответ в запрошенном формате, сервер должен вернуть **406 Not Acceptable**.
* **`Authorization`:** Передача токена (обычно `Bearer <token>`).
* **`Location`:** Используется при ответе `201 Created`. Содержит абсолютный URL созданного ресурса.
* **`X-Request-ID` / `X-Correlation-ID`:** Сквозной идентификатор запроса. Клиент генерирует UUID, и он пробрасывается через все логи всех сервисов. Это позволяет отследить путь одного запроса.
* **`Vary`:** Подсказывает кэширующим прокси, по каким заголовкам кэш должен отличаться (например, `Vary: Accept-Encoding, Authorization`).
* **`Cache-Control`:** Управление кэшированием (например, `no-cache, no-store, must-revalidate`).
* **`ETag (Entity Tag)`:** Хеш ресурса. Позволяет экономить трафик. Если ресурс не менялся, сервер вернет `304 Not Modified`.
* **`Prefer`:** Заголовок `Prefer: return=minimal` или `Prefer: return=representation`. Позволяет клиенту указать, хочет ли он получить созданный объект в ответе на POST или только его ID.
* **`Idempotency-Key`:** В нестабильных сетях клиент может отправить POST дважды из-за таймаута. Сервер сохраняет результат первого запроса с этим ключом и при повторе просто отдает тот же ответ, не выполняя логику.


## Стандарты ответов

* **JSON:API:** Очень строгий и мощный стандарт. Описывает всё: от пагинации до фильтрации и включения связанных ресурсов (include).
* **RFC 7807 (Problem Details):** Стандарт для описания ошибок. Несовместим с `JSON:API`.


## HATEOAS (Hypermedia as the Engine of Application State)
В идеальном REST API ответ сервера должен содержать ссылки на следующие возможные действия. В реальности это реализуют редко - сложно в реализации.


## Best practices

### Использовать существительные вместо глаголов

* ❌ `/getAllUsers`, `/updateUser/123`
* ✅ `GET /users`, `PATCH /users/123`

### Использовать множественное число 

`/users`, `/articles`, `/orders`

### Kebab-case для URL

`GET /v1/user-profiles` лучше, чем `userProfiles` или `user_profiles`.

### Версионирование

Есть 2 основных подхода:
* **В URL (`/v1/users`, `/v2/users`):** Самый наглядный и простой способ. Легко кешировать, легко тестировать.
* **Media Type Versioning (`Accept: application/vnd.myapi.v1+json`):** Более правильный с точки зрения REST подход (Content Negotiation), но сложнее в отладке и часто ломает кеширование в браузерах/прокси.

Для большинства больших систем URL-версионирование выигрывает за счет простоты эксплуатации.

Стандартные OAuth2 роуты (`/oauth/token`) обычно **не версионируют**. Протокол OAuth2 — это уже стандарт. Если меняется логика выпуска токена, то скорее меняется версия протокола или параметры запроса. Большинство OAuth-серверов (Keycloak, Auth0, Google) используют пути без `/v1/`.

### Иерархия вложенности и плоская структура URL (Shallow Routing)

`GET /articles/5/comments`

`GET /v1/organizations/5/accounts/8/tests` — классическая проблема глубокой вложенности.
Если ресурс можно однозначно идентифицировать по его ID (он уникален в рамках всей базы, а не только внутри родителя), нужно использовать **Shallow Routing**.

* **Коллекции оставляем вложенными:** `GET /organizations/5/accounts` (получить список аккаунтов конкретной организации).
* **Конкретный ресурс выносим в корень:** `GET /accounts/8`.
* **Почему это лучше?**
    1.  **Лаконичность:** URL короче и чище.
    2.  **Гибкость:** Если аккаунт «переедет» в другую организацию, ссылка на него не изменится.
    3.  **Производительность:** Клиенту не нужно знать ID всей цепочки родителей, чтобы сделать запрос к конкретному элементу.


### Пагинация

**Offset-based:** `GET /users?limit=20&offset=100`

**Cursor-based:** `GET /users?limit=20&after_id=540`

При ответе с коллекцией нужно возвращать не просто массив, а объект, где данные обернуты в поле (`items`/`data`), а рядом лежат метаданные:
```json
{
  "items": [...],
  "_metadata": {
    "total_count": 1050,
    "limit": 20,
    "offset": 40,
    "links": {
      "self": "/v1/users?offset=40&limit=20",
      "next": "/v1/users?offset=60&limit=20",
      "prev": "/v1/users?offset=20&limit=20"
    }
  }
}
```

### Фильтрация и поиск

Антипаттерн - по эндпоинту на каждый фильтр.
Лучше использовать query-параметры с поддержкой разных операторов:

`GET /cars?price[gte]=1000&color[in]=red,blue&sort=-created_at&category=tech&status=active`
* `gte/lte` — больше/меньше.
* `in` — перечисление.
* `-` перед полем — сортировка по убыванию.


### Частичные ответы (Sparse Fieldsets)

Если объект огромный, а фронтенду нужны только конкретные поля:
`GET /users/12?fields=id,email,name`
