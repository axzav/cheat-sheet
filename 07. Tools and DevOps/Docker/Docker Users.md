# Docker user management

Пользователь по умолчанию внутри контейнера - **root** (0:0).

Это приводит к следующим проблемам:
* Безопасность. При компрометации контейнера злоумышленник получает root. Root в контейнере может влиять на хост (при определенных настройках)
* При bind mount директории хоста в контейнер файлы, созданные процессом в контейнере, могут принадлежать другому пользователю на хосте:
  * Логи создаются с неправильными правами
  * Нельзя удалить/изменить файлы с хоста
  * Проблемы с кешем, сессиями и другими директориями
* Работа с файловой системой контейнера. Даже без volumes важно, чтобы процесс мог писать только в разрешенные директории и чтобы файлы принадлежали нужному пользователю

Для решения этих проблем можно:
* Запускать контейнер от конкретного пользователя
* Настроить UID/GID в dockerfile


## Запуск контейнера от конкретного пользователя

Можно передать пользователя для запуска основного процесса контейнера на этапе исполнения:
```shell
docker run -u 1000:1000 ...
```
Или
```yaml
# docker-compose.yml
services:
  php-fpm:
    build: .
    user: "1000:1000"
```

В некоторых случаях это сработает нормально, но в других будут проблемы. Если пользователь не создан внутри Dockerfile, то это может привести к ошибкам в процессе выполнения.
Также это может привести к проблемам с доступом к файлам.

Лучший вариант - **настройка UID/GID в dockerfile**


## Настройка UID/GID в dockerfile

На этапе билда добавляются аргументы USER_ID и GROUP_ID. Создается соответсвующий пользователь, директориям назначаются нужные права и основной процесс запускается от конкретного пользователя.

**dockerfile**
```dockerfile
FROM php:8.2-fpm

# Получаем UID/GID через build args
ARG USER_ID=1000
ARG GROUP_ID=1000

# Создаем пользователя с нужным UID/GID
RUN groupadd -g ${GROUP_ID} appuser || true && \
    useradd -u ${USER_ID} -g ${GROUP_ID} -m -s /bin/bash appuser || true

# Устанавливаем рабочую директорию
WORKDIR /var/www

# Меняем владельца рабочей директории
RUN chown -R appuser:appuser /var/www

# Переключаемся на непривилегированного пользователя
USER appuser

# выполнится от appuser
RUN composer install

# CMD тоже выполнится от appuser
CMD ["php-fpm"]
```

В `docker-compose.yaml` передаются аргументы для билда. Если нужен bind mount с теми же правами, что и у пользователя хоста, то `USER_ID` и `GROUP_ID` указываются те же что и на хосте.
Можно дополнительно указать `user` в compose, но если в Dockerfile все настроено верно, то это не нужно.

**docker-compose.yaml**
```yaml
services:
  php-fpm:
    build:
      context: .
      dockerfile: Dockerfile
      args:
        USER_ID: ${USER_ID:-1000}  # Из .env или по умолчанию 1000
        GROUP_ID: ${GROUP_ID:-1000}
    volumes:
      - ./:/var/www
    user: "${USER_ID:-1000}:${GROUP_ID:-1000}"  # Можно дополнительно указать пользователя в compose
```

**.env**
```dotenv
USER_ID=1000
GROUP_ID=1000
```
Или
```shell
USER_ID=$(id -u) GROUP_ID=$(id -g) docker compose up
```

Еще можно заменить UID/GID пользователя в контейнере. Например, если это сборка из базового образа в котором создается пользователь и нужно настроить bind mount для него.

```dockerfile
RUN groupmod -o -g ${GROUP_ID} www-data && \
    usermod -o -u ${USER_ID} -g www-data www-data 

RUN chown -R www-data:www-data /var/www
```


## macOS vs Linux

**Linux**
* UID/GID совпадают между хостом и контейнером
* Файлы, созданные в контейнере, имеют такие же права на хосте
* Правильно настроенный менеджмент пользователей **необходим**

**macOS**
* Docker Desktop на macOS использует виртуальную машину (VM)
* UID/GID в контейнере не совпадают с UID/GID на macOS хосте
* Файлы автоматически маппятся к пользователю macOS, но реальные UID/GID в VM могут отличаться
* В контейнере лучше использовать фиксированный UID/GID (например, 1000:1000)
* С настройкой пользователей **можно не заморачиваться**, Docker Desktop решает большинство проблем автоматически


## alpine vs debian

debian:
```dockerfile
RUN groupadd --gid 2000 node \
  && useradd --uid 2000 --gid node --shell /bin/bash --create-home node
```

alpine:
```dockerfile
RUN addgroup -g 2000 node \
    && adduser -u 2000 -G node -s /bin/sh -D node
```


## Best practices

* НЕ запускать контейнеры как root
* создавать пользователя в Dockerfile с нужным UID/GID
* использовать build args для передачи UID/GID
* На Linux использовать реальные UID/GID хоста
* На macOS использовать фиксированные значения (1000:1000) или значения из VM
* не делать динамический usermod в рантайме
* использовать Rootless Docker
