## Путь запроса

Postgres

Parser - синтаксический анализатор. проверяет корректность запроса с точки зрения синтаксиса. Создает дерево (что за дерево?) Parse tree 
Analyzer/Analyser - семантический анализатор. Проверяет что существуют сущности к которым идет запрос (таблицы, поля) query tree
Rewriter - хз, что-то там еще делает
Planner - планировщик создает все планы выполнения запроса и выбирает самый лучший из них (cost-based planner). Передает на исполнение plan tree - как раз его можно посмотреть в explain
Executor - уже конкретно выполняет запрос plan tree

Mysql

Схема примерно такая-же, но на последнем этапе исполнитель запроса делает API call на движок базы данных. 
В mysql существует множество движков баз данных (MyISAM, InnoDB, etc) и планировщик не знает ничего о внутреннем устройстве этих движков и не имеет доступа к их внутреннему представлению. Таким образом планировщик создает свой запрос на основе абстрактного интерфейса движка.

В postgres нет такого понятия как движок базы данных и планировщик знает как устроено хранилище данных, а также обладает более богатой статистикой по данным в базе, поэтому планировщик postgresql более эффективный, чем планировщик mysql.

## MVCC (Multi Version Concurrency Control)

В постргес данные для разных версий строк хранятся в виде новой записи в базе. Таким образом, если много транзакций делают записи в базу, то таблица будет расти до момента пока ее очистит автовакуум. Если какой-то запрос будет проходить по таблице последовательным сканированием, то это скажется на производительности

В мускуле записи транзакций хранятся в отдельном временном хранилище UNDO Log

OLAP - запросы в основном на чтение. Влияние MVCC низкое
OLTP - надо смотреть какая нагрузка и в случае постгреса надо подкрутить автовакуум

В постгресс все индексы некластерные (вторичные). 
Видимость данных в индексе?
Постгресс поддерживает большое количество различных типов индексов
Index Hints не существуют в постгресс. Планировщик сам найдет нужные индексы


В мускуле при объявлении внешнего ключа он автоматически создает вторичный ключ на внешней таблице. Постгрес этого не делает

В мускуле есть кластерные индексы. В таблице может быть 1 кластерный индекс и несколько некластерных индексов.
В явном виде поддекрживается только B-tree индекс. 
Есть Hash индексы но они используются неявно самим движком InnoDB в служебных целях
Поддерживаются Index Hints
