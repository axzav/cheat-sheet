# Partitioning

Partitioning divides a large table into smaller, more manageable pieces called partitions. Each partition can be stored and managed independently.

## Benefits

1. **Performance**: Queries can scan only relevant partitions
2. **Maintenance**: Operations on individual partitions are faster
3. **Storage**: Can store partitions on different storage
4. **Query Optimization**: Partition pruning eliminates irrelevant partitions

## Partitioning Types

### Range Partitioning
Partitions based on range of values.

**PostgreSQL:**
```sql
CREATE TABLE sales (
    id INT,
    sale_date DATE,
    amount DECIMAL
) PARTITION BY RANGE (sale_date);

CREATE TABLE sales_2023 PARTITION OF sales
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE sales_2024 PARTITION OF sales
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
```

**MySQL:**
```sql
CREATE TABLE sales (
    id INT,
    sale_date DATE,
    amount DECIMAL
) PARTITION BY RANGE (YEAR(sale_date)) (
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026)
);
```

### List Partitioning
Partitions based on specific values.

**PostgreSQL:**
```sql
CREATE TABLE users (
    id INT,
    country VARCHAR(2),
    name VARCHAR(100)
) PARTITION BY LIST (country);

CREATE TABLE users_us PARTITION OF users
    FOR VALUES IN ('US', 'CA', 'MX');

CREATE TABLE users_eu PARTITION OF users
    FOR VALUES IN ('GB', 'FR', 'DE');
```

**MySQL:**
```sql
CREATE TABLE users (
    id INT,
    country VARCHAR(2),
    name VARCHAR(100)
) PARTITION BY LIST COLUMNS (country) (
    PARTITION p_us VALUES IN ('US', 'CA', 'MX'),
    PARTITION p_eu VALUES IN ('GB', 'FR', 'DE')
);
```

### Hash Partitioning
Partitions based on hash function.

**PostgreSQL:**
```sql
CREATE TABLE orders (
    id INT,
    user_id INT,
    order_date DATE
) PARTITION BY HASH (user_id);

CREATE TABLE orders_0 PARTITION OF orders;
CREATE TABLE orders_1 PARTITION OF orders;
CREATE TABLE orders_2 PARTITION OF orders;
CREATE TABLE orders_3 PARTITION OF orders;
```

**MySQL:**
```sql
CREATE TABLE orders (
    id INT,
    user_id INT,
    order_date DATE
) PARTITION BY HASH (user_id)
PARTITIONS 4;
```

### Composite Partitioning
Combines multiple partitioning strategies.

**PostgreSQL:**
```sql
CREATE TABLE sales (
    id INT,
    region VARCHAR(10),
    sale_date DATE,
    amount DECIMAL
) PARTITION BY LIST (region);

CREATE TABLE sales_us PARTITION OF sales
    FOR VALUES IN ('US')
    PARTITION BY RANGE (sale_date);

CREATE TABLE sales_us_2023 PARTITION OF sales_us
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
```

## Partition Management

### Adding Partitions

**PostgreSQL:**
```sql
CREATE TABLE sales_2025 PARTITION OF sales
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
```

**MySQL:**
```sql
ALTER TABLE sales ADD PARTITION (
    PARTITION p2025 VALUES LESS THAN (2026)
);
```

### Dropping Partitions

**PostgreSQL:**
```sql
DROP TABLE sales_2023;  -- Drops partition
```

**MySQL:**
```sql
ALTER TABLE sales DROP PARTITION p2023;
```

### Merging Partitions

**MySQL:**
```sql
ALTER TABLE sales
    REORGANIZE PARTITION p2023, p2024 INTO (
        PARTITION p2023_2024 VALUES LESS THAN (2025)
    );
```

## Partition Pruning

The database automatically eliminates partitions that don't contain relevant data:

```sql
-- Only scans sales_2024 partition
SELECT * FROM sales WHERE sale_date = '2024-06-15';

-- Scans all partitions (no pruning)
SELECT * FROM sales WHERE amount > 1000;
```

## Best Practices

1. **Choose Right Key**: Partition by frequently queried column
2. **Balance Size**: Keep partitions roughly equal size
3. **Limit Count**: Too many partitions can hurt performance
4. **Indexes**: Create indexes on partition key
5. **Maintenance**: Plan for adding/dropping partitions
6. **Queries**: Design queries to enable partition pruning
7. **Monitoring**: Monitor partition sizes and usage

## When to Use Partitioning

- **Large Tables**: Tables with millions/billions of rows
- **Time-Series Data**: Data naturally organized by time
- **Geographic Data**: Data organized by region
- **Archival**: Easy to drop old partitions
- **Parallel Operations**: Operations can run in parallel

## When NOT to Use Partitioning

- Small tables (< 1GB)
- Tables without clear partition key
- Frequent cross-partition queries
- Complex joins across partitions
- Limited maintenance window

## Partitioning vs Sharding

- **Partitioning**: Single database, logical separation
- **Sharding**: Multiple databases, physical separation
- Use partitioning for single-server optimization
- Use sharding for horizontal scaling across servers
