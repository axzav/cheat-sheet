# Index Tuning

Index tuning (настройка индексов) — процесс оптимизации индексов для улучшения производительности запросов при минимизации накладных расходов на операции записи.

## Принципы настройки индексов

### Баланс между чтением и записью
- Индексы ускоряют чтение, но замедляют запись
- Каждая INSERT/UPDATE/DELETE требует обновления индексов
- Слишком много индексов может снизить производительность записи

### Селективность
- Высокая селективность: много уникальных значений (email, ID)
- Низкая селективность: мало уникальных значений (пол, статус)
- Индексы эффективнее на столбцах с высокой селективностью

### Частота использования
- Индексировать столбцы, часто используемые в WHERE, JOIN, ORDER BY
- Избегать индексов на редко используемых столбцах

## Анализ запросов

### Определение медленных запросов

```sql
-- PostgreSQL: pg_stat_statements
SELECT query, mean_exec_time, calls 
FROM pg_stat_statements 
ORDER BY mean_exec_time DESC 
LIMIT 10;

-- MySQL: Slow query log
SHOW VARIABLES LIKE 'slow_query_log';
SET GLOBAL slow_query_log = 'ON';
```

### EXPLAIN для анализа

```sql
-- PostgreSQL
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'user@example.com';

-- MySQL
EXPLAIN SELECT * FROM users WHERE email = 'user@example.com';
```

### Ключевые метрики
- **Seq Scan / Full Table Scan**: Указывает на отсутствие или неиспользование индекса
- **Index Scan**: Использование индекса
- **Index Only Scan**: Запрос полностью покрыт индексом (лучший вариант)
- **Cost**: Оценка стоимости операции

## Стратегии создания индексов

### Индексы для WHERE

```sql
-- Частые поиски по email
CREATE INDEX idx_email ON users(email);

-- Составные условия
CREATE INDEX idx_user_status ON users(user_id, status) 
WHERE status = 'active';
```

### Индексы для JOIN

```sql
-- Foreign key обычно автоматически индексируется
-- Но можно создать составной индекс для сложных JOIN
CREATE INDEX idx_order_user_date ON orders(user_id, order_date);
```

### Индексы для ORDER BY

```sql
-- Если часто сортируем по created_at
CREATE INDEX idx_created_at ON users(created_at DESC);

-- Составной индекс для WHERE + ORDER BY
CREATE INDEX idx_user_created ON orders(user_id, created_at DESC);
```

### Индексы для GROUP BY

```sql
-- Группировка по статусу
CREATE INDEX idx_status ON orders(status);

-- Составной индекс для WHERE + GROUP BY
CREATE INDEX idx_user_status ON orders(user_id, status);
```

## Оптимизация составных индексов

### Порядок столбцов

**Правило**: Наиболее селективные столбцы первыми, затем по частоте использования.

```sql
-- Плохо: status имеет низкую селективность
CREATE INDEX idx_status_user ON orders(status, user_id);

-- Хорошо: user_id более селективный
CREATE INDEX idx_user_status ON orders(user_id, status);
```

### Leftmost Prefix Rule

```sql
CREATE INDEX idx_composite ON orders(user_id, order_date, status);

-- Используется:
WHERE user_id = 1
WHERE user_id = 1 AND order_date = '2024-01-01'
WHERE user_id = 1 AND order_date > '2024-01-01'

-- НЕ используется:
WHERE order_date = '2024-01-01'
WHERE status = 'pending'
```

### Covering Indexes

Индекс, содержащий все столбцы, необходимые для запроса.

```sql
-- PostgreSQL
CREATE INDEX idx_covering ON orders(user_id) 
INCLUDE (order_date, total);

-- MySQL (составной индекс)
CREATE INDEX idx_covering ON orders(user_id, order_date, total);
```

## Partial Indexes

Индексировать только подмножество строк для уменьшения размера.

```sql
-- Только активные пользователи
CREATE INDEX idx_active_email ON users(email) 
WHERE status = 'active';

-- Только недавние заказы
CREATE INDEX idx_recent_orders ON orders(user_id) 
WHERE created_at > '2024-01-01';
```

## Expression Indexes

Индексы на вычисляемых значениях.

```sql
-- Поиск по email без учета регистра
CREATE INDEX idx_email_lower ON users(LOWER(email));

-- Поиск по году
CREATE INDEX idx_year ON orders(EXTRACT(YEAR FROM order_date));
```

## Мониторинг индексов

### Неиспользуемые индексы

```sql
-- PostgreSQL
SELECT schemaname, tablename, indexname, idx_scan 
FROM pg_stat_user_indexes 
WHERE idx_scan = 0 
ORDER BY pg_relation_size(indexrelid) DESC;

-- MySQL
SELECT * FROM sys.schema_unused_indexes;
```

### Размер индексов

```sql
-- PostgreSQL
SELECT 
    indexname,
    pg_size_pretty(pg_relation_size(indexname::regclass)) AS size
FROM pg_indexes 
WHERE tablename = 'users';

-- MySQL
SHOW TABLE STATUS LIKE 'users';
```

### Фрагментация

```sql
-- PostgreSQL: перестроить индекс
REINDEX INDEX idx_email;

-- MySQL: оптимизировать таблицу
OPTIMIZE TABLE users;
```

## Удаление индексов

### Когда удалять
- Индекс не используется (проверить через мониторинг)
- Индекс дублирует другой индекс
- Накладные расходы на запись превышают выгоду от чтения

```sql
-- Удалить неиспользуемый индекс
DROP INDEX idx_unused_column;
```

## Специфичные оптимизации по СУБД

### PostgreSQL

```sql
-- Настройка fillfactor
CREATE INDEX idx_email ON users(email) WITH (fillfactor = 80);

-- Параллельное создание индекса
CREATE INDEX CONCURRENTLY idx_email ON users(email);

-- Использование индекса для сортировки
SET enable_sort = off;  -- Заставить использовать индекс
```

### MySQL

```sql
-- Настройка InnoDB
SET GLOBAL innodb_buffer_pool_size = 1073741824;  -- 1GB

-- Адаптивный hash index
SET GLOBAL innodb_adaptive_hash_index = ON;

-- Оптимизация для чтения
SET GLOBAL read_buffer_size = 2097152;
```

## Метрики производительности

### До оптимизации
- Время выполнения запроса
- Количество full table scans
- Размер индексов
- Частота использования индексов

### После оптимизации
- Сравнить время выполнения
- Проверить использование индексов через EXPLAIN
- Мониторить влияние на операции записи

## Типичные ошибки

### Слишком много индексов
- Каждый индекс замедляет INSERT/UPDATE/DELETE
- Занимает место на диске
- Усложняет оптимизацию

### Неправильный порядок в составных индексах
- Индекс не используется из-за leftmost prefix rule
- Низкая эффективность

### Индексы на низкоселективных столбцах
- Малая польза от индекса
- Лучше использовать full table scan

### Игнорирование мониторинга
- Неиспользуемые индексы остаются в базе
- Накладные расходы без выгоды
