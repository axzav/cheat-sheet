# B-tree

B-tree (B-дерево) — наиболее распространенная структура данных для индексов в реляционных базах данных. Это самобалансирующееся дерево поиска, которое поддерживает отсортированные данные и позволяет выполнять поиск, вставку и удаление за логарифмическое время.

## Характеристики B-tree

### Структура
- **Узлы**: Каждый узел содержит ключи и указатели на дочерние узлы
- **Листья**: Листовые узлы содержат ключи и указатели на данные таблицы
- **Балансировка**: Дерево автоматически балансируется при вставке и удалении
- **Высота**: Логарифмическая высота относительно количества элементов

### Порядок дерева
- **Order (порядок)**: Максимальное количество дочерних узлов у внутреннего узла
- Обычно выбирается так, чтобы узел помещался в один блок диска (page)

## Преимущества B-tree

### Универсальность
- Поддерживает поиск на равенство (equality search)
- Поддерживает поиск по диапазону (range queries)
- Поддерживает сортировку (ORDER BY)
- Поддерживает поиск по префиксу (prefix matching)

### Производительность
- **Поиск**: O(log n) временная сложность
- **Вставка**: O(log n) временная сложность
- **Удаление**: O(log n) временная сложность
- Эффективное использование дискового пространства

### Оптимизация для диска
- Узлы соответствуют блокам диска (pages)
- Минимизирует количество обращений к диску
- Хорошая локальность данных

## Как работает B-tree

### Поиск
1. Начать с корневого узла
2. Сравнить искомый ключ с ключами в узле
3. Перейти к соответствующему дочернему узлу
4. Повторять до достижения листового узла
5. Найти ключ в листе и получить указатель на данные

### Вставка
1. Найти правильную позицию в листовом узле
2. Вставить ключ
3. Если узел переполнен, разделить его
4. Поднять средний ключ в родительский узел
5. Повторять разделение вверх по дереву при необходимости

### Удаление
1. Найти ключ в листовом узле
2. Удалить ключ
3. Если узел стал слишком пустым, объединить с соседним
4. Обновить родительские узлы при необходимости

## B-tree в базах данных

### PostgreSQL
- Используется по умолчанию для большинства индексов
- Поддерживает различные типы данных
- Оптимизирован для работы с диском

```sql
-- Создание B-tree индекса (по умолчанию)
CREATE INDEX idx_email ON users(email);

-- Явное указание типа
CREATE INDEX idx_email ON users USING BTREE (email);
```

### MySQL (InnoDB)
- Используется для primary key и secondary indexes
- Clustered index на primary key
- Secondary indexes содержат указатели на primary key

```sql
-- Создание B-tree индекса
CREATE INDEX idx_email ON users(email);
```

## Операции, поддерживаемые B-tree

### Equality Search (Поиск на равенство)
```sql
SELECT * FROM users WHERE email = 'user@example.com';
```
Индекс эффективно находит точное совпадение.

### Range Queries (Запросы по диапазону)
```sql
SELECT * FROM orders WHERE order_date BETWEEN '2024-01-01' AND '2024-12-31';
SELECT * FROM products WHERE price > 100 AND price < 500;
```
Индекс эффективно находит все значения в диапазоне.

### Sorting (Сортировка)
```sql
SELECT * FROM users ORDER BY created_at DESC;
```
Данные в индексе уже отсортированы, что ускоряет сортировку.

### Prefix Matching (Поиск по префиксу)
```sql
SELECT * FROM users WHERE name LIKE 'John%';
```
B-tree может эффективно находить значения, начинающиеся с префикса.

### Partial Key Search (Поиск по части ключа)
Для составных индексов можно искать по левой части ключа благодаря правилу leftmost prefix.

## Составные B-tree индексы

### Порядок столбцов важен
```sql
CREATE INDEX idx_composite ON orders (user_id, order_date, status);
```

Этот индекс может использоваться для:
- `WHERE user_id = ?`
- `WHERE user_id = ? AND order_date = ?`
- `WHERE user_id = ? AND order_date = ? AND status = ?`
- `WHERE user_id = ? AND order_date > ?` (range на последнем условии)

Но НЕ может эффективно использоваться для:
- `WHERE order_date = ?` (без user_id)
- `WHERE status = ?` (без предыдущих столбцов)

### Leftmost Prefix Rule
Индекс используется только если запрос начинается с левого столбца индекса.

## Оптимизация B-tree

### Fill Factor
Процент заполнения страниц индекса. Оставляет место для будущих вставок.

```sql
-- PostgreSQL
CREATE INDEX idx_email ON users(email) WITH (fillfactor = 80);

-- MySQL
-- Настраивается через innodb_fill_factor
```

### Maintenance
- **REINDEX**: Перестроение индекса для устранения фрагментации
- **VACUUM / OPTIMIZE**: Очистка и оптимизация таблицы и индексов
- **ANALYZE**: Обновление статистики для оптимизатора

## Сравнение с другими структурами

### B-tree vs Hash Index
- **B-tree**: Поддерживает диапазоны, сортировку, O(log n)
- **Hash**: Только равенство, O(1), но без диапазонов

### B-tree vs B+tree
- **B-tree**: Ключи могут быть в любом узле
- **B+tree**: Все ключи в листьях, листья связаны (используется в MySQL InnoDB)

## Когда использовать B-tree

### Идеально подходит для
- Большинства случаев использования индексов
- Запросов с WHERE, ORDER BY, JOIN
- Столбцов с высокой кардинальностью
- Запросов по диапазону

### Может быть не оптимальным для
- Только точных поисков на равенство (можно рассмотреть Hash)
- Столбцов с очень низкой кардинальностью
- Очень больших таблиц с естественной сортировкой (можно рассмотреть BRIN)

## Рекомендации

1. Использовать B-tree как выбор по умолчанию для большинства индексов
2. Правильно упорядочивать столбцы в составных индексах
3. Регулярно обслуживать индексы (REINDEX, VACUUM)
4. Мониторить размер и фрагментацию индексов
5. Анализировать использование индексов через EXPLAIN
