# Hash Indexes

Hash indexes use hash functions to map keys to index entries, providing very fast lookups for equality queries.

## How Hash Indexes Work

1. Hash function computes hash value from key
2. Hash value maps to bucket/slot
3. Direct access to bucket (O(1) average case)
4. Collision handling for same hash values

## Characteristics

### Advantages
- **Fast Equality Lookups**: O(1) average time complexity
- **Simple Structure**: Direct key-to-value mapping
- **Memory Efficient**: Compact storage

### Disadvantages
- **No Range Queries**: Cannot efficiently support <, >, BETWEEN
- **No Sorting**: Cannot return results in sorted order
- **Collision Handling**: Performance degrades with many collisions
- **Not Suitable for All Data Types**: Works best with fixed-size keys

## PostgreSQL Hash Indexes

### Creating Hash Index

```sql
CREATE INDEX idx_email_hash ON users USING HASH (email);
```

### When to Use

- Equality queries only (`WHERE email = 'value'`)
- High-cardinality columns
- Fixed-size data types
- Frequent exact lookups

### Limitations

- PostgreSQL hash indexes don't support unique constraints (until v10)
- Not WAL-logged (until v10) - can be lost in crash
- No support for multi-column indexes
- Cannot be used for sorting

## MySQL Hash Indexes

### InnoDB Adaptive Hash Index

Automatically created by InnoDB for frequently accessed index pages:

```sql
-- Check adaptive hash index status
SHOW ENGINE INNODB STATUS;

-- Disable adaptive hash index
SET GLOBAL innodb_adaptive_hash_index = OFF;
```

### Memory Storage Engine

```sql
CREATE TABLE hash_table (
    id INT,
    name VARCHAR(100),
    INDEX idx_name USING HASH (name)
) ENGINE=MEMORY;
```

## Hash Index vs B-tree Index

| Feature | Hash Index | B-tree Index |
|---------|-----------|--------------|
| Equality Lookup | O(1) | O(log n) |
| Range Queries | Not supported | Supported |
| Sorting | Not supported | Supported |
| Partial Keys | Not supported | Supported |
| Prefix Matching | Not supported | Supported |
| Multi-column | Limited | Full support |

## Use Cases

1. **Lookup Tables**: Fast key-value lookups
2. **Session Storage**: Quick session retrieval
3. **Cache Tables**: Frequently accessed data
4. **Join Operations**: Hash joins use hash indexes
5. **Unique Constraints**: Fast uniqueness checks

## Best Practices

1. Use for exact match queries only
2. High cardinality columns work best
3. Monitor collision rates
4. Consider B-tree for range queries
5. Use with fixed-size data types when possible
6. Test performance vs B-tree indexes

## Hash Functions

Common hash functions used:
- **MD5**: Fast but not cryptographically secure
- **SHA-1/SHA-256**: More secure, slower
- **CRC32**: Fast checksum
- **MurmurHash**: Fast, good distribution
- **CityHash**: Google's fast hash

## Collision Resolution

### Chaining
- Each bucket contains linked list
- Collisions stored in same bucket
- Simple but can degrade performance

### Open Addressing
- Find next available slot
- Linear probing, quadratic probing
- Better cache locality

## When NOT to Use Hash Indexes

- Need range queries
- Need sorted results
- Low cardinality columns
- Frequently updated columns (rehashing overhead)
- Multi-column indexes needed
- Prefix matching required
