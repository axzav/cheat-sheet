# Hash Indexes

Hash index (хеш-индекс) использует хеш-функции для сопоставления ключей с записями индекса, обеспечивая очень быстрый поиск для запросов на равенство.

## Как работают Hash Indexes

1. Хеш-функция вычисляет хеш-значение из ключа
2. Хеш-значение сопоставляется с bucket/slot
3. Прямой доступ к bucket (O(1) в среднем случае)
4. Обработка коллизий для одинаковых хеш-значений

## Характеристики

### Преимущества
- **Быстрый поиск на равенство**: O(1) средняя временная сложность
- **Простая структура**: Прямое сопоставление ключ-значение
- **Эффективное использование памяти**: Компактное хранение

### Недостатки
- **Нет запросов по диапазону**: Не может эффективно поддерживать <, >, BETWEEN
- **Нет сортировки**: Не может возвращать результаты в отсортированном порядке
- **Обработка коллизий**: Производительность снижается при большом количестве коллизий
- **Не подходит для всех типов данных**: Лучше работает с ключами фиксированного размера

## Hash Indexes в PostgreSQL

### Создание Hash Index

```sql
CREATE INDEX idx_email_hash ON users USING HASH (email);
```

### Когда использовать

- Только запросы на равенство (`WHERE email = 'value'`)
- Столбцы с высокой кардинальностью
- Типы данных фиксированного размера
- Частые точные поиски

### Ограничения

- Hash indexes в PostgreSQL не поддерживают unique constraints (до версии 10)
- Не логируются в WAL (до версии 10) — могут быть потеряны при сбое
- Нет поддержки многоколоночных индексов
- Нельзя использовать для сортировки

## Hash Indexes в MySQL

### InnoDB Adaptive Hash Index

Автоматически создается InnoDB для часто используемых страниц индекса:

```sql
-- Проверить статус adaptive hash index
SHOW ENGINE INNODB STATUS;

-- Отключить adaptive hash index
SET GLOBAL innodb_adaptive_hash_index = OFF;
```

### Memory Storage Engine

```sql
CREATE TABLE hash_table (
    id INT,
    name VARCHAR(100),
    INDEX idx_name USING HASH (name)
) ENGINE=MEMORY;
```

## Hash Index vs B-tree Index

| Характеристика | Hash Index | B-tree Index |
|----------------|-----------|--------------|
| Поиск на равенство | O(1) | O(log n) |
| Запросы по диапазону | Не поддерживается | Поддерживается |
| Сортировка | Не поддерживается | Поддерживается |
| Частичные ключи | Не поддерживается | Поддерживается |
| Поиск по префиксу | Не поддерживается | Поддерживается |
| Многоколоночные | Ограничено | Полная поддержка |

## Случаи использования

1. **Lookup таблицы**: Быстрый поиск по ключу-значению
2. **Хранение сессий**: Быстрое получение сессий
3. **Кеш-таблицы**: Часто используемые данные
4. **Операции JOIN**: Hash joins используют hash indexes
5. **Unique constraints**: Быстрая проверка уникальности

## Рекомендации

1. Использовать только для точного совпадения
2. Лучше работают со столбцами высокой кардинальности
3. Мониторить частоту коллизий
4. Рассматривать B-tree для запросов по диапазону
5. Использовать с типами данных фиксированного размера, когда возможно
6. Тестировать производительность по сравнению с B-tree indexes

## Хеш-функции

Распространенные хеш-функции:
- **MD5**: Быстрая, но не криптографически стойкая
- **SHA-1/SHA-256**: Более стойкая, медленнее
- **CRC32**: Быстрая контрольная сумма
- **MurmurHash**: Быстрая, хорошее распределение
- **CityHash**: Быстрая хеш-функция от Google

## Разрешение коллизий

### Chaining (Цепочки)
- Каждый bucket содержит связанный список
- Коллизии хранятся в том же bucket
- Просто, но может снижать производительность

### Open Addressing (Открытая адресация)
- Поиск следующего доступного слота
- Linear probing, quadratic probing
- Лучшая локальность кеша

## Когда НЕ использовать Hash Indexes

- Нужны запросы по диапазону
- Нужны отсортированные результаты
- Столбцы с низкой кардинальностью
- Часто обновляемые столбцы (накладные расходы на перехеширование)
- Нужны многоколоночные индексы
- Требуется поиск по префиксу
