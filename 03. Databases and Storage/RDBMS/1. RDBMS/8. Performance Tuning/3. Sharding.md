# Шардирование (Sharding)

Шардирование — техника горизонтального разделения данных между несколькими базами данных на разных серверах для масштабирования и повышения производительности.

## Основные концепции

### Что такое шардирование

Шардирование разделяет большую таблицу на меньшие части (shards), каждая из которых хранится на отдельном сервере или в отдельной базе данных. Это позволяет распределить нагрузку и масштабировать систему горизонтально.

### Отличие от партиционирования

- **Партиционирование**: Логическое разделение на одном сервере
- **Шардирование**: Физическое разделение на нескольких серверах

## Стратегии шардирования

### Range-Based Sharding (Шардирование по диапазонам)

Разделение данных по диапазонам значений ключа шардирования.

**Пример:**
- Shard 1: user_id от 1 до 1000000
- Shard 2: user_id от 1000001 до 2000000
- Shard 3: user_id от 2000001 до 3000000

**Преимущества:**
- Простота реализации
- Легко определить, в каком shard находятся данные

**Недостатки:**
- Неравномерное распределение данных
- Hot spots при неравномерном распределении запросов

### Hash-Based Sharding (Шардирование по хэшу)

Разделение данных с использованием хэш-функции от ключа шардирования.

**Пример:**
```python
shard_id = hash(user_id) % num_shards
```

**Преимущества:**
- Более равномерное распределение данных
- Меньше hot spots

**Недостатки:**
- Сложнее определить shard без вычисления хэша
- Сложнее перебалансировка

### Directory-Based Sharding (Шардирование по справочнику)

Использование справочника (lookup table) для определения shard.

**Пример:**
```sql
-- Таблица справочника
CREATE TABLE shard_directory (
    user_id INT PRIMARY KEY,
    shard_id INT
);
```

**Преимущества:**
- Гибкость в выборе shard
- Легко перебалансировать данные

**Недостатки:**
- Дополнительный запрос для определения shard
- Справочник может стать узким местом

### Geographic Sharding (Географическое шардирование)

Разделение данных по географическому признаку.

**Пример:**
- Shard US: Пользователи из США
- Shard EU: Пользователи из Европы
- Shard ASIA: Пользователи из Азии

## Ключ шардирования (Shard Key)

Ключ шардирования — колонка или набор колонок, используемых для определения shard.

### Выбор ключа шардирования

**Критерии:**
- Равномерное распределение данных
- Минимизация cross-shard запросов
- Учет паттернов доступа к данным

**Примеры:**
- `user_id` для таблицы пользователей
- `order_id` для таблицы заказов
- `tenant_id` для multi-tenant приложений

## Cross-Shard Queries (Межшардовые запросы)

Запросы, затрагивающие несколько shards, сложнее и медленнее.

### Стратегии обработки

1. **Избегать cross-shard запросов**: Проектировать запросы для работы с одним shard
2. **Fan-out queries**: Выполнять запросы на всех shards и объединять результаты
3. **Дублирование данных**: Хранить необходимые данные на каждом shard
4. **Materialized views**: Создавать агрегированные представления

## Ребалансировка (Rebalancing)

Процесс перераспределения данных между shards для поддержания баланса.

### Когда нужна ребалансировка

- Неравномерное распределение данных
- Добавление новых shards
- Удаление shards
- Изменение стратегии шардирования

### Подходы к ребалансировке

1. **Offline rebalancing**: Остановка системы на время ребалансировки
2. **Online rebalancing**: Ребалансировка без остановки системы
3. **Consistent hashing**: Минимизация перемещения данных при добавлении shards

## Реализация шардирования

### На уровне приложения

Приложение само определяет shard для каждого запроса:

```python
def get_shard_id(user_id, num_shards):
    return hash(user_id) % num_shards

def get_user(user_id):
    shard_id = get_shard_id(user_id, 4)
    shard_connection = shard_connections[shard_id]
    return shard_connection.query("SELECT * FROM users WHERE id = ?", user_id)
```

### Использование proxy/middleware

Промежуточный слой автоматически направляет запросы на нужный shard:

- **Vitess**: Для MySQL
- **Citus**: Для PostgreSQL
- **MongoDB Sharding**: Встроенное шардирование

### Database-native sharding

Встроенные механизмы шардирования в СУБД:

- **PostgreSQL с Citus**: Расширение для шардирования
- **MySQL Cluster**: Встроенное шардирование
- **MongoDB**: Встроенное шардирование

## Примеры конфигурации

### PostgreSQL с Citus

```sql
-- Создать распределенную таблицу
SELECT create_distributed_table('users', 'user_id');

-- Запрос автоматически выполняется на нужном shard
SELECT * FROM users WHERE user_id = 12345;
```

### Vitess (MySQL)

```yaml
# Конфигурация keyspace
keyspaces:
  - name: user_keyspace
    shards:
      - name: "-80"
        tablets:
          - type: master
            host: shard1-master
      - name: "80-"
        tablets:
          - type: master
            host: shard2-master
```

## Проблемы и решения

### Проблемы шардирования

1. **Сложность запросов**: Cross-shard запросы сложнее
2. **Транзакции**: Сложнее поддерживать транзакции между shards
3. **Ребалансировка**: Требует тщательного планирования
4. **Операционная сложность**: Управление несколькими базами данных

### Решения

1. **Использовать готовые решения**: Vitess, Citus, MongoDB
2. **Планировать архитектуру**: Учитывать шардирование на этапе проектирования
3. **Мониторинг**: Отслеживать распределение данных и производительность
4. **Документация**: Документировать стратегию шардирования

## Best Practices

1. **Выбирать правильный ключ шардирования**: Обеспечивать равномерное распределение
2. **Минимизировать cross-shard запросы**: Проектировать запросы для одного shard
3. **Планировать ребалансировку**: Заранее продумать стратегию
4. **Мониторить распределение данных**: Отслеживать размеры shards
5. **Использовать connection pooling**: Для эффективного управления соединениями
6. **Документировать топологию**: Поддерживать актуальную документацию
7. **Тестировать failover**: Обеспечивать отказоустойчивость
8. **Начинать с простого**: Не усложнять без необходимости

## Когда использовать шардирование

- Очень большие таблицы (миллиарды строк)
- Необходимость горизонтального масштабирования
- Географическое распределение пользователей
- Multi-tenant приложения
- Высокая нагрузка на запись

## Когда не использовать шардирование

- Небольшие или средние базы данных
- Частые cross-shard запросы
- Сложные транзакции между shards
- Недостаточные ресурсы для управления несколькими базами данных
- Можно решить проблему вертикальным масштабированием
