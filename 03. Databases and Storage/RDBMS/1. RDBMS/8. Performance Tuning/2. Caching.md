# Кэширование (Caching)

Кэширование — техника хранения часто используемых данных в быстродоступной памяти для ускорения доступа к данным и снижения нагрузки на базу данных.

## Типы кэширования

### Кэширование на уровне базы данных

#### Buffer Pool (Буферный пул)

Основной механизм кэширования страниц данных в памяти.

**PostgreSQL:**
```ini
# postgresql.conf
shared_buffers = 256MB  # Общая память для кэширования
effective_cache_size = 1GB  # Оценка доступной памяти для планировщика
```

**MySQL (InnoDB):**
```ini
# my.cnf
innodb_buffer_pool_size = 1G  # Размер буферного пула
innodb_buffer_pool_instances = 4  # Количество экземпляров
```

#### Query Cache (Кэш запросов)

Кэширование результатов запросов (устарело в MySQL 8.0, удалено).

**MySQL (до версии 8.0):**
```ini
query_cache_type = 1
query_cache_size = 64M
```

### Кэширование на уровне приложения

#### In-Memory Cache

Использование систем кэширования в памяти приложения:

- **Redis**: In-memory data structure store
- **Memcached**: Distributed memory caching system
- **Hazelcast**: In-memory data grid

#### Application-Level Caching

Кэширование результатов запросов в приложении:

```python
# Пример с использованием декоратора кэширования
from functools import lru_cache

@lru_cache(maxsize=1000)
def get_user_by_id(user_id):
    return db.query("SELECT * FROM users WHERE id = ?", user_id)
```

## Стратегии кэширования

### Cache-Aside (Lazy Loading)

Приложение управляет кэшем:

1. Проверить кэш
2. Если данных нет, загрузить из базы данных
3. Сохранить в кэш
4. Вернуть данные

```python
def get_user(user_id):
    # Проверить кэш
    user = cache.get(f"user:{user_id}")
    if user:
        return user
    
    # Загрузить из БД
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)
    
    # Сохранить в кэш
    cache.set(f"user:{user_id}", user, ttl=3600)
    
    return user
```

### Write-Through

Запись одновременно в кэш и базу данных:

1. Записать в базу данных
2. Записать в кэш
3. Вернуть результат

### Write-Back (Write-Behind)

Запись сначала в кэш, затем асинхронно в базу данных:

1. Записать в кэш
2. Вернуть результат
3. Асинхронно записать в базу данных

### Refresh-Ahead

Предварительное обновление кэша до истечения срока действия:

1. Проверить время до истечения TTL
2. Если близко к истечению, обновить в фоне
3. Вернуть данные из кэша

## Инвалидация кэша (Cache Invalidation)

### Time-Based Expiration (TTL)

Автоматическое удаление данных после истечения времени:

```python
cache.set("key", "value", ttl=3600)  # TTL в секундах
```

### Event-Based Invalidation

Удаление кэша при изменении данных:

```python
def update_user(user_id, data):
    # Обновить в БД
    db.update("users", user_id, data)
    
    # Инвалидировать кэш
    cache.delete(f"user:{user_id}")
```

### Tag-Based Invalidation

Группировка кэшированных данных по тегам для массовой инвалидации:

```python
# Сохранить с тегом
cache.set("user:1", user_data, tags=["users", "user:1"])

# Инвалидировать все данные с тегом
cache.delete_by_tag("users")
```

## Кэширование запросов

### Кэширование результатов запросов

Кэшировать результаты часто выполняемых запросов:

```sql
-- Кэшировать результат агрегации
SELECT COUNT(*) FROM orders WHERE status = 'pending';
```

### Materialized Views (Материализованные представления)

Представления с физически сохраненными данными:

**PostgreSQL:**
```sql
CREATE MATERIALIZED VIEW sales_summary AS
SELECT 
    DATE_TRUNC('month', sale_date) AS month,
    SUM(amount) AS total_sales
FROM sales
GROUP BY DATE_TRUNC('month', sale_date);

-- Обновить материализованное представление
REFRESH MATERIALIZED VIEW sales_summary;
```

## Мониторинг кэширования

### Метрики производительности

- **Cache Hit Ratio**: Процент попаданий в кэш
- **Cache Miss Ratio**: Процент промахов кэша
- **Cache Size**: Размер используемого кэша
- **Eviction Rate**: Скорость вытеснения данных из кэша

### PostgreSQL

```sql
-- Проверить статистику буферов
SELECT * FROM pg_stat_bgwriter;

-- Проверить использование shared_buffers
SELECT 
    sum(blks_hit) * 100.0 / (sum(blks_hit) + sum(blks_read)) AS cache_hit_ratio
FROM pg_stat_database;
```

### MySQL

```sql
-- Проверить использование InnoDB Buffer Pool
SHOW STATUS LIKE 'Innodb_buffer_pool%';

-- Cache hit ratio
SELECT 
    (1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)) * 100 
    AS cache_hit_ratio
FROM 
    (SELECT VARIABLE_VALUE AS Innodb_buffer_pool_reads 
     FROM performance_schema.global_status 
     WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads') AS reads,
    (SELECT VARIABLE_VALUE AS Innodb_buffer_pool_read_requests 
     FROM performance_schema.global_status 
     WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests') AS requests;
```

## Best Practices

1. **Кэшировать часто читаемые, редко изменяемые данные**: Статические справочники, конфигурации
2. **Устанавливать разумные TTL**: Баланс между актуальностью и производительностью
3. **Использовать иерархию кэшей**: L1 (приложение) → L2 (Redis) → L3 (БД)
4. **Мониторить cache hit ratio**: Цель — >90% для часто используемых данных
5. **Планировать инвалидацию**: Обеспечивать консистентность данных
6. **Использовать компрессию**: Для больших объектов в кэше
7. **Настраивать размеры кэшей**: В зависимости от доступной памяти и рабочего набора данных
8. **Документировать стратегии кэширования**: Для понимания поведения системы

## Когда использовать кэширование

- Часто читаемые данные
- Результаты сложных вычислений
- Данные из внешних источников (API)
- Сессии пользователей
- Статические справочники

## Когда не использовать кэширование

- Часто изменяемые данные
- Критически важные данные, требующие актуальности
- Данные, которые используются редко
- Данные, размер которых превышает доступную память
