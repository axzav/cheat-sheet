Микросервисная архитектура предполагает разделение приложения на множество мелких, автономных сервисов, каждый из которых выполняет определенную бизнес-функцию. Для успешного создания и управления такими системами используются различные паттерны проектирования, которые помогают решать общие проблемы и обеспечивают надежность, масштабируемость и управляемость микросервисов. Вот некоторые из наиболее распространенных микросервисных паттернов:

# Паттерны управления сервисами

## Service Registry (Регистратор сервисов)
Регистратор сервисов управляет информацией о доступных микросервисах и их местоположении. Когда сервисы запускаются, они регистрируются в регистраторе, и другие сервисы могут использовать эту информацию для обнаружения и взаимодействия с ними.

Пример: Eureka, Consul, Zookeeper.

## Service Discovery (Обнаружение сервисов)
Обнаружение сервисов позволяет микросервисам находить друг друга через регистратор сервисов. Существует два типа обнаружения: клиентское (клиент напрямую запрашивает регистратор) и серверное (обнаружение выполняется через промежуточный слой, такой как API Gateway).


# Паттерны взаимодействия между сервисами

## API Gateway
Действует как единая точка входа для всех клиентов, обеспечивая маршрутизацию запросов к соответствующим микросервисам, а также функции безопасности, авторизации, и ограничения скорости.

Пример: NGINX, Kong, AWS API Gateway.

## Circuit Breaker (Автоматический выключатель)
Этот паттерн защищает систему от каскадных отказов, прекращая попытки вызова микросервиса, если он обнаруживает, что сервис не отвечает или отвечает с ошибками. После периода времени попытки возобновляются.

Пример: Hystrix, Resilience4j.

# Паттерны управления данными

## Database per Service (База данных на сервис)
Каждый микросервис имеет собственную базу данных, что способствует автономности и независимости сервисов. Это помогает избежать тесных связей между сервисами на уровне данных.

## Saga (Сага)
Паттерн саги используется для управления распределенными транзакциями, разбивая их на серию локальных транзакций, координируемых через обмен сообщениями.

Пример: Axon Framework, NServiceBus.


# Паттерны обмена сообщениями

## Event Sourcing (Событийное хранилище)
Событийное хранилище сохраняет состояние системы как последовательность событий. Вместо сохранения текущего состояния, система сохраняет все изменения в виде событий, что позволяет воспроизводить текущее состояние, пройдя через все события.

## CQRS (Command Query Responsibility Segregation)
Разделяет модель данных для операций чтения и записи. Модель команд (commands) обрабатывает изменения состояния, а модель запросов (queries) отвечает за чтение данных.


# Паттерны развертывания

## Blue-Green Deployment (Синее-зеленое развертывание)
Этот паттерн предполагает наличие двух идентичных производственных сред: синей и зеленой. Одна из них активна, а другая используется для развертывания новой версии. После успешного тестирования новая версия переключается и становится активной.

## Canary Release (Канареечный релиз)
Новая версия сервиса развертывается на небольшом количестве узлов, чтобы можно было протестировать её с реальными пользователями и минимизировать риски. Если всё проходит успешно, новая версия разворачивается на остальных узлах.
