# Roles

В `Symfony` по умолчанию реализована система `RBAC0`/`RBAC1`.
Система `RBAC0` подразумевает модель `User → Role → Permission`.
Система `RBAC1` подразумевает иерархию ролей.

**Например:**
```yaml
security:
    role_hierarchy:
        ROLE_SUPER_ADMIN: ROLE_ADMIN
        ROLE_ADMIN:       ROLE_USER
```

В стандартном упрощенном подходе проверки в коде будут такими (**Role-centric Authorization**):
```php
$this->isGranted('ROLE_SUPER_ADMIN');
```

Если требуется добавить проверки на `Permission`, то в стандартном подходе делают так:
```php
$this->isGranted('ROLE_ORG_DELETE');
```

Т.е. в `Symfony` в стандартном подходе считается, что `Role` = `Permission`.
Однако роли и permissions — это разные вещи. Делать что-то вроде `ROLE_ORG_DELETE` - **признак плохого дизайна**.
Это приводит к **Role Explosion** - система ролей становится плохо масштабируемой. На 10 ресурсов и 10 действий появится 100 ролей.

Рекомендуемый путь - иерархия **ROLE → PERMISSION → SUBJECT → CONTEXT**.

Представим на примере такой системы:
```text
User
 │
 ├ member → Organization
 │            │
 │            └ owns → Account
 │                        │
 │                        └ owns → Campaign
 │
 └ member → Account
```

Пользователь может быть `ORGANIZATION_ADMIN` в каких-то конкретных организациях и/или быть `ACCOUNT_ADMIN`/`ACCOUNT_MANAGER` в каких-то аккаунтах.
`ORGANIZATION_ADMIN` при этом имеет доступ к аккаунтам в организациях.

В системе будут глобальные **Platform roles**, а также **Resource roles** которые настраиваются для каждого пользователя и ресурса.
В данной системе будет применяться комбинация систем доступа RBAC + ReBAC + ABAC


### Уровень 1 — ROLE (глобальная роль пользователя)

Роль — это грубый уровень доступа (coarse-grained). Она отвечает только на вопрос - "кто этот пользователь в системе?".

Представим такой набор ролей:

**Platform roles**
Это роли на уровне приложения для стаффа и пользователей, **RBAC0** - глобальные роли.
Эти роли хранятся в таблице пользователей. Можно также построить иерархию ролей (**RBAC1**):
```yaml
security:
    role_hierarchy:
        ROLE_SUPER_ADMIN: [ROLE_MODERATOR, ROLE_SUPPORT]
        ROLE_MODERATOR: ROLE_SUPPORT
        ROLE_SUPPORT: ROLE_USER
        ROLE_USER:
```

**Resource roles**
Контекстно зависимые роли отвечают за разграничение доступа к различным ресурсам в системе - **ReBAC**.
Эти роли вычисляются в `Voter` в зависимости от `SUBJECT` (Organization/Account) в императивной модели. В декларативной модели используется ReBAC-движок.
Эти роли хранятся уже не в таблице пользователей, а в **ReBAC-хранилище**/membership таблице, в зависимости от реализации.
```text
ORGANIZATION_ADMIN         # пользовательская роль администратора организации
ACCOUNT_ADMIN              # пользовательские роли уровня аккаунта
ACCOUNT_MANAGER
ACCOUNT_VIEWER
```

В модели данных это может выглядеть так:
```text
User
 ├ roles: [ROLE_USER, ROLE_SUPPORT, ...]
 └ memberships

OrganizationMembership
 ├ user_id
 ├ organization_id
 └ role (ADMIN / MEMBER)

AccountMembership
 ├ user_id
 ├ account_id
 └ role (ADMIN / MANAGER / VIEWER)
```

`ROLE` — Это **shortcut для bypass**. Например, может быть сделано так:
```php
#[Security("
    is_granted('ROLE_SUPER_ADMIN') 
    or is_granted('ORG_MEMBERSHIP_EDIT', organization)
")]
```
Однако лучше вынести проверку роли в `Voter` а в контроллере оставлять только проверку `PERMISSION`.

Проверки ролей этого уровня можно добавлять для контроллеров без контекста, например обращение в службу поддержки или доступ к внутренним интерфейсам.


### Уровень 2/3 — PERMISSION/SUBJECT (что можно делать, над чем выполняется действие)

`Permission` — это действие. `Permission` отвечает на вопрос - "что пользователь пытается сделать?".
```text
ORG_VIEW
ORG_EDIT
ORG_MEMBERSHIP_VIEW
ORG_MEMBERSHIP_EDIT

ACCOUNT_VIEW
ACCOUNT_EDIT
ACCOUNT_DELETE
```

`Subject` — это конкретный объект. `Subject` отвечает на вопрос - "над чем выполняется действие?".
```text
Account
Organization
Campaign
User
```

В контроллерах будут такие выражения:
```php
#[Security("is_granted('ORG_MEMBERSHIP_EDIT', organization)")]
#[Security("is_granted('ACCOUNT_DELETE', organization)")]
```

Для проверок `Permissions` будут вызываться `Voters`.


### 3. Уровень 4 — CONTEXT

`CONTEXT` это любые дополнительные условия, влияющие на доступ.
Такими условиями могут быть:
* tenant (для этого примера это связь аккаунта с организацией)
* environment
* request context (request ip / api key)
* ownership
* feature flags
* status объекта (например `Campaign.archived` → readonly)

Проверки уровня `CONTEXT` происходят в коде `Voter`.


### `Voter`

**Принцип хорошего дизайна - один voter на домен**:
```text
AccountVoter
    → ACCOUNT_VIEW
    → ACCOUNT_EDIT
    → ACCOUNT_DELETE
OrganizationVoter
    ...
CampaignVoter
    ...
```
Еще лучше - **Policy Voters.**

```php
class AccountVoter extends Voter
{
    public const ACCOUNT_VIEW = 'ACCOUNT_VIEW';
    public const ACCOUNT_EDIT = 'ACCOUNT_EDIT';

    protected function supports(string $attribute, $subject): bool
    {
        return $subject instanceof Account;
    }

    protected function voteOnAttribute(
        string $attribute,
        $account,
        TokenInterface $token
    ): bool {
        
        // ABAC - тут на основе атрибутов SUBJECT принимается решение о доступе
        if ($attribute === self::ACCOUNT_EDIT && $account->isArchived()) {
            return false;
        }
        
        $user = $token->getUser();
        $roles = $token->getRoleNames();

        // RBAC
        if (in_array('ROLE_SUPER_ADMIN', $roles)) {
            return true;
        }

        // RBAC
        if (in_array('ROLE_SUPPORT', $roles)) {
            return $attribute === self::ACCOUNT_VIEW;
        }

        // ReBAC императивная модель
        if ($this->membershipService->hasAccountRole($user, $account, 'ADMIN')) {
            return true;
        }

        // ReBAC императивная модель
        if ($this->membershipService->hasOrganizationRole($user, $account->getOrganization(), 'ADMIN')) {
            return true;
        }

        // Или ReBAC декларативная модель
        return $this->authz->check(
            subject: "user:{$user->getId()}",
            relation: strtolower($attribute),
            object: "campaign:{$account->getId()}"
        );

        return false;
    }
}
```
