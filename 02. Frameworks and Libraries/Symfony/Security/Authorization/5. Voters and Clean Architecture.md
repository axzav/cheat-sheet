# Voters and Clean Architecture

Стандартный подход `Symfony Voter` и `DDD/Clean Architecture` конфликтуют, если их использовать напрямую.
В DDD бизнес-правила должны быть в `Domain` или `Application`, а не в `framework`, а `Symfony Voter` — это **framework infrastructure**.

В зависимости от `CONTEXT` нужно правильно выбирать где хранить логику доступа:
```text
Domain
    Policies
    Ownership
    Status rules
    Tenant relations

Application
    Global roles
    Feature flags

Infrastructure
    Request context
    Environment
```


## Domain/Application Authorization

В DDD доступ — это **часть бизнес-логики**. Например, `Account` может редактировать только его владелец.
Это **доменное правило**, а не security-правило.

Такое правило должно находиться либо в **Domain entity/Domain Policy**:
```text
Domain
 ├ Policy
 │   ├ AccountPolicy
 │   ├ OrganizationPolicy
```

Или в `AuthorizationService` на уровне **Application**:
```text
Application
 ├ Authorization
 │   ├ AccountPolicy
 │   ├ OrganizationPolicy
```


## Voter

В Clean Architecture `Voter` — `Infrastructure / Interface layer` и не должен содержать бизнес-логики. Он должен только вызвать **policy**.
Symfony → Voter → Policy → Domain.

```text
src/
 ├ Domain
 ├ Application
 ├ Infrastructure
 │   └ Security
 │       └ Voter
```



## Controller Authorization vs Application Layer Authorization

Есть два основных варианта, где разместить процесс авторизации.

### Вариант 1 — Symfony style, Controller

**Controller**
```php
class AccountController
{
    #[Security("is_granted('ACCOUNT_EDIT', account)")]
    public function update(Account $account): JsonResponse
    {
        ...
    }
}
```

**Voter**
```php
class AccountVoter extends Voter
{
    public function __construct(
        private AccountPolicy $policy
    ) {}

    protected function voteOnAttribute(
        string $attribute,
        $account,
        TokenInterface $token
    ): bool {

        $user = $token->getUser();

        return $this->policy->canEdit($user, $account);
    }
}
```

**Policy (Domain/Application)**
```php
class AccountPolicy
{
    public function canEdit(User $user, Account $account): bool
    {
        if ($user->isSuperAdmin()) {
            return true;
        }

        if ($user->isOrganizationAdmin($account->organizationId)) {
            return true;
        }

        return $user->hasAccountRole($account->id, 'ADMIN');
    }
}
```

В таком случае будет задействован функционал фреймворка для авторизации со всей логикой `AuthorizationChecker`, `AccessDecisionManager` и тд.
`Voter` выступает тут как тонкий адаптер для бизнес-логики.
Это framework-coupled решение.


### Вариант 2 — Чистая DDD-модель, без Voters

Это **более чистая архитектура**, DDD style. Authorization полностью внутри `Application`. 
Symfony Security используется только для:
* authentication
* token
* user extraction
* basic route protection

**Controller:**
```php
class UpdateAccountController
{
    public function __invoke(
        Request $request,
        int $accountId
    ): JsonResponse {

        $command = new UpdateAccountCommand(
            $this->currentUser(),
            $accountId,
            $request->toArray()
        );

        $this->handler->handle($command);

        return new JsonResponse(['status' => 'ok']);
    }
}
```

**Application handler:**
```php
class UpdateAccountHandler
{
    public function __construct(
        private AccountRepository $accounts,
        private AccountPolicy $policy
    ) {}

    public function handle(UpdateAccountCommand $cmd): void
    {
        $account = $this->accounts->get($cmd->accountId);

        if (!$this->policy->canEdit($cmd->user, $account)) {
            throw new AccessDeniedException();
        }

        $account->update(...);
    }
}
```

**Policy:**
```php
class AccountPolicy
{
    public function canEdit(User $user, Account $account): bool
    {
        if ($user->isSuperAdmin()) {
            return true;
        }

        if ($user->isOrganizationAdmin($account->organizationId)) {
            return true;
        }

        return $user->hasAccountRole($account->id, 'ADMIN');
    }
}
```


### CLI

В `Symfony Style` подходе с `Voters` есть проблема с авторизацией для CLI. Security layer symfony работает только для HTTP запроса.
`Security Token` все еще можно создать вручную внутри команды, но тогда возникает вопрос - кто пользователь в CLI?
Это может быть, например system user (ROLE_SYSTEM, ROLE_SUPER_ADMIN) но это уже логика приложения, а не framework.

В `DDD` подходе делается иначе, процесс авторизации считается частью use case и handler всегда получает актора - `UpdateAccountCommand(user, accountId)`.
Тогда для логики не имеет значение в каком контексте вызывается handler, т.к. авторизация находится уровнем ниже:

```php
class UpdateAccountCommand extends Command
{
    public function execute()
    {
        $command = new UpdateAccountCommand(
            $this->systemUser,
            $this->accountId
        );

        $handler->handle($command);
    }
}
```

```text
Entry point (HTTP / CLI / Worker)
 ↓
Application handler
 ↓
Authorization policy
 ↓
Domain
```
